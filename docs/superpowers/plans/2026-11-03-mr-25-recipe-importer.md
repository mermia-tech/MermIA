# MR-25 part 2: recipe template and importer (plan)

Status: approved 2026-11-03. Decisions: 1 = (b) propose with `new_ingredient`, MR-32 creates it on approval; 2 = the hold rule goes in PR 1 here; 3 = ids in `diff`; 4 = manual source. Branch `MR-25-recipe-importer`, stacked on #73 (`MR-23-recetas`). Part 1 (engine) is PR #62.

## 1. Goal and scope
An owner fills a template we generate and sends it back. Every recipe batch (from our template or from the SR Recetas parser) becomes `recipe.upsert` pending changes: `proposed_via='import'`, status `pending`, a readable before/after `diff`, and an audit row written in the same step. Nothing writes `recipe` or `recipe_line`.

- **This ticket:**
  - the template writer and parser, with its registry entry;
  - loader support for `catalog` batches, turning them into pending changes;
  - matching dishes and ingredients;
  - the unit check and yield cleanup;
  - skipping unchanged recipes and duplicate proposals;
  - holding a single bad recipe instead of the whole file.
- **MR-32 does the apply step** for `recipe.upsert`:
  - write the new recipe version, `confirmed`, with its lines;
  - set `effective_from` to the approval date, so past costs don't change;
  - check `base_version` against the `recipe_version` of the recipe in effect;
  - write the audit row on apply and recompute costs;
  - keep `required_role` = `manager`.
- **MR-37:** the "Cambio pendiente" message, and one tap to approve all of a batch's changes (found via `diff->>'batch_id'`).
- **MR-35:** generate the template for the pilot's top dishes and load the real SR Recetas export.
- **Out of scope:** sub-recipes in the template (needs `RecipeIn.produces_ingredient_name`) and SR costs.

## 2. Template
Generated by our code and prefilled with the tenant's menu (03 C.2). The owner or manager fills it in Excel or Google Sheets. All text is in Mexican Spanish.

- **Writer:** `apps/api/src/mermia_api/ingestion/templates/recetas.py`. A pure `render(data) -> bytes`, `build(conn, tenant_id, location_id)`, and a CLI: `uv run python -m mermia_api.ingestion.templates.recetas --tenant … [--location …] --out …`. Column and sheet names live only in the parser module; the writer imports them.
- **Sheet "Instrucciones":** about 8 short lines.
- **Sheet "Recetas":** a title block (location; "Plantilla de recetas MermIA"; "Versión 1"; "Fecha: dd/mm/aaaa"), then the header `Clave | Platillo | Porciones | Insumo | Cantidad | Unidad | Rendimiento % | Notas`.
  - Dishes are listed by units sold in the last 28 days.
  - A dish with an existing recipe is prefilled with its current lines, in base units.
  - A dish without one gets its first row plus 8 blank rows.
  - The dish name is written once; the rows below it belong to the same dish.
- **Sheet "Insumos":** a read-only reference (`Insumo | Unidad base | Rendimiento normal % | Categoría`). It feeds an Insumo dropdown (warning style, so a new name can still be typed) and a Unidad dropdown (g, kg, ml, l, pza).
- **Differences from the SR layout:**
  - "Platillo" instead of "Producto", so the two can't be mistaken for each other;
  - grouped rows instead of the dish repeated on every row;
  - Porciones (`yield_qty`) added;
  - no Clave insumo and no Costo;
  - parser `mermia.plantilla_recetas@v1`, `source_kind=manual`, `grain=catalog`.

## 3. Steps

### PR 1: catalog batches become pending changes (~350 code + ~350 test lines)
1. **`parsers/sr_recetas.py`: hold a bad recipe, not the whole file.** A recipe with any error-level line is left out of the batch. Its row issues stay, plus one `sr.recipe_held` issue naming the dish. This prevents proposing a recipe with a dropped line, which would understate its cost. Update `test_sr_recetas.py`; the golden doesn't change.
2. **New `ingestion/recipes.py`:** `propose_recipes(conn, tenant, location, batch_id, batch, proposed_by)`.
   - **Dish:** use `loader._find_item`. A code-and-name or name match is accepted. A match by code only is held (`recipe.item_code_mismatch`). No match is held (`recipe.item_unknown`). Menu items are never created.
   - **Ingredient:** match by normalized name across the tenant's ingredients.
     - Two ingredients with the same name: held (`recipe.ingredient_ambiguous`).
     - Not found: see decision 1.
     - One Clave insumo under several names in the file: a warning (`recipe.ingredient_code_names`).
   - **Sub-recipe:** an ingredient produced by another recipe (e.g. salsa verde) becomes a sub-recipe line, and its yield override is dropped.
   - **Unit check:** `unit` must be g, ml or pza and must equal `ingredient.base_unit`. Otherwise the recipe is held (`recipe.unit_unknown` or `recipe.unit_mismatch`), so the line is never costed.
   - **Yield override equal to the ingredient's default:** stored as null, so a later change to the default reaches the line.
   - **Unchanged recipe** (same lines and `yield_qty` as `app.recipe_of_record`): nothing is proposed. An identical `pending` proposal is also skipped.
   - **Otherwise,** insert the `pending_change` row and its `audit_log` row (`pending_change.propose`):
     - `kind='recipe.upsert'`, `target_type='menu_item'`, `base_version` = the current `recipe_version` (or null), `required_role='manager'`, `expires_at=now()+24h`;
     - payload validated with `RecipeUpsertProposal`;
     - `diff`: `{batch_id, parser, menu_item, before, after, added, removed, changed}`.
3. **`loader.py`:**
   - Add `Grain.catalog: "recipes"` to `SUPPORTED`. The catalog totals check is `totals.lines == len(recipes)`.
   - Skip the rules for sales batches.
   - Never call `apply_batch` for catalog batches. Status is `parsed` when at least one recipe was proposed or unchanged, and `rejected` when all were held.
   - Write `stats.proposed/unchanged/held`.
   - Add an optional `proposed_by` to `load()` and `pending_change_ids` to `LoadResult`.
   - **DB tests** in `test_recipe_import.py`:
     - the SR sample gives 15 unchanged;
     - an edit to pastor gives 1 pending change with the right diff and an audit row;
     - a unit mismatch, an ambiguous ingredient, a dish matched by code only and an unknown dish are each held;
     - an unknown ingredient follows decision 1;
     - salsa verde becomes a sub-recipe line;
     - an override equal to the default is stored as null;
     - the same file twice is a duplicate;
     - an identical proposal is not filed twice;
     - `test_load_never_writes_recipe_tables`;
     - change `test_an_unsupported_grain_is_rejected` to use `purchase`.

### PR 2: the template (~300 code + ~250 test lines, plus the sample)
4. Move `UNITS` and the quantity and yield helpers into `parsers/_recipe_units.py`, with no behaviour change.
5. **New parser `parsers/mermia_recetas.py`:**
   - recognized by its title and the Platillo header;
   - the dish name carries down to the rows below it;
   - Porciones becomes `yield_qty`;
   - units are converted and an optional yield is read;
   - each problem holds only its own dish, with a `plantilla.*` issue.
   - Tests: `test_mermia_recetas.py`, including that the SR and template formats can't be mistaken for each other.
6. **Writer and CLI** (section 2). Tests: the headers, the dropdowns, and that the prefilled recipes match the seed.
7. **Registry and sample:**
   - register the template parser first; the `UnknownReport` message lists "la plantilla de recetas de MermIA";
   - commit `fixtures/templates/plantilla_recetas_v1_L1.xlsx` and its golden, written from the seed by the CLI;
   - extend `test_golden.py` to read `fixtures/templates/`;
   - **round-trip DB test:** generate the template, parse it and load it, giving 15 unchanged. Then edit one quantity and add a dish, giving the right pending changes.

## 5. Contract impact
None: `batch.py`, `pending.py` and `db/models.py` don't change, and there is no migration. These would need both devs' approval, and only if chosen: `RecipeLine.ingredient_id`, a `pending_change.batch_id` column, `ingredient.external_id`, `RecipeIn.produces_ingredient_name`.

## 6. Decisions
1. **Unknown ingredient:**
   - (a) hold the recipe; or
   - (b) propose it with `new_ingredient: true`, and MR-32 creates the ingredient on approval.
   - Recommended: (b).
2. **Holding one recipe instead of the whole file** changes the SR parser from #73. It can go in PR 1 here (recommended) or as a commit on #73.
3. **Matched ingredient ids** live in `diff` (recommended, no contract change), or in a new `RecipeLine.ingredient_id` field.
4. **Template uploads use a manual source** per location, created by MR-30 (recommended), or the loader's source-kind check is relaxed.

Note: recipes apply to the whole tenant, so a Centro manager's upload proposes changes for every location. Only the owner can approve `recipe.upsert` in the seed, and MR-32 should keep it that way.
